BRO TEXT FILE GUIDE (CANONICAL ORDER)

Purpose

This guide defines how BRO text files are used so future sessions do not drift.

Authority Order

1. BRO_CANONICAL_DOCTRINE.txt
   - Primary authority for strategy doctrine, workflow rules, and non-negotiable invariants.

2. BRO_EDGE_DOCTRINE.txt
   - Canonical edge-origin, execution-mode, and edge-truth constraints.

3. BRO_PAPER_HARNESS_REALISM_DOCTRINE.txt
   - Canonical realism boundaries for paper harness evidence interpretation.

4. BRO_OUTCOME_TRUTH_DOCTRINE.txt
   - Canonical outcome attribution and claim-boundary doctrine (measurement only).

5. BRO_MODULE_ARCHITECTURE.txt
   - Canonical architecture boundaries and module responsibility contract.

6. docs/BRO_WALLET_DOCTRINE.md
   - Canonical capital-authority, wallet-health, and deployable-capital doctrine.

7. BRO_SITREP_DOCTRINE.txt
   - Operator sitrep summary for current phase and priorities.
   - Summary only. It must not contradict BRO_CANONICAL_DOCTRINE.txt.

8. requirements.txt
   - Dependency manifest only. Not a doctrine source.

Downstream BRO-Specific Policy Surfaces

- `docs/DOCTRINE_RUNBOOK.md`
  - BRO-specific downstream runtime/runbook policy surface.
  - It may define current fighter-specific timing, stage, and execution policy.
  - It must not silently override items `1` through `5`.
- `docs/SOLAR_SLUG_MAKER_CIRCUIT_SCHEMATIC.md`
  - BRO-local maker pathway/reference surface.
  - Design/pathway truth only; not runtime authority by itself.
- `docs/GALAXY_MEGA_MAKER_CANNON_BLUEPRINT_2026-04-28.md`
  - BRO-local intended maker-weapon doctrine anchor.
  - It defines the intended late-window maker posture (`15-20s`, sweet spot
    `10-15s`) for doctrine cleanup and support-surface alignment.
  - It is not automatic proof that current runtime already matches that
    posture.
- `docs/BRO_WEAPON_NOMENCLATURE.md`
  - Mnemonic alias surface only.

Repo-Level Current Truth Screen

- `docs/PROJECT_TRUTH_STATE.md`
  - Front-of-house repo current-truth surface for active operator use.
- `docs/CURRENT_BASELINE.md`
  - Baseline/reference/history surface; not the top-level current-truth entrypoint.

Conflict Rule

If any file conflicts with BRO_CANONICAL_DOCTRINE.txt, the doctrine file wins.

Update Discipline

- Keep doctrine updates explicit and versioned by date.
- Avoid copying doctrine fragments into multiple files without cross-reference.
- Prefer referencing the canonical doctrine file over rewriting doctrine text in summaries.
- Any architecture change must preserve canonical domain separation and fail-closed behavior.
